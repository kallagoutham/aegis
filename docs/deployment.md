# Deployment

## Requirements

| Component | Minimum | Notes |
|---|---|---|
| PostgreSQL | 16 | With the `vector` and `pg_trgm` extensions |
| Python | 3.12 | 3.13 is what the image ships |
| Memory | 512 MB per replica | 1 GB with large log analysis |
| Model provider | OpenAI-compatible | Any gateway exposing `/v1` |

---

## Docker Compose

The bundled stack (`docker-compose.yml`) runs the API, PostgreSQL with pgvector,
Prometheus, and Grafana.

```bash
make env ENV=production
# edit .env.production
make up ENV=production
make logs
```

For a production-like run, remove the `./aegis:/app/aegis:ro` volume mount from
the `api` service — it exists for live reload during development and lets host
code override the image contents.

---

## The image

Multi-stage. The builder carries `build-essential` and `libpq-dev`; the runtime
carries only `libpq5`, `curl`, the virtualenv, and the application — roughly
400 MB of compilers stay behind, which is both size and attack surface.

```bash
make build ENV=production
docker run --rm -p 8000:8000 --env-file .env.production aegis:production
```

Layer ordering is deliberate: dependencies install from `pyproject.toml` before
application code is copied, so editing code does not invalidate the slow layer.

The container runs as unprivileged uid 1001, and `HEALTHCHECK` probes
`/health/live` only — a healthcheck touching the database would make Docker kill
healthy containers during a database blip.

## Migrations

The entrypoint waits for PostgreSQL, then runs `alembic upgrade head`, then
`exec`s the command.

Migrations run in the entrypoint rather than a separate init container because
the schema and the code that reads it ship in the same image, so they cannot
skew. Alembic takes an advisory lock, so concurrent replica starts serialise
rather than racing.

Disable when a separate job owns migrations:

```bash
RUN_MIGRATIONS=false
```

Manual operation:

```bash
make migrate                          # upgrade head
make migrate-sql                      # print SQL without applying (for a DBA)
make migrate-down                     # roll back one
make migration M="add widget table"   # autogenerate
```

**Always read an autogenerated migration before applying it.** Alembic cannot
see index operator classes, generated columns, or extensions — the initial
migration writes those by hand for exactly that reason.

CI runs `upgrade → downgrade base → upgrade` on every push. A downgrade path
nobody exercises is a downgrade path that does not work, discovered during the
rollback of a bad deploy.

## Kubernetes

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: aegis
spec:
  replicas: 3
  selector:
    matchLabels: { app: aegis }
  template:
    metadata:
      labels: { app: aegis }
    spec:
      containers:
        - name: aegis
          image: ghcr.io/your-org/aegis:1.0.0
          ports:
            - containerPort: 8000

          env:
            - name: APP_ENV
              value: production
            - name: LOG_TO_FILE
              value: "false"          # the platform captures stdout
            - name: POSTGRES_POOL_SIZE
              value: "10"             # see connection budget below
          envFrom:
            - secretRef: { name: aegis-secrets }

          # Liveness must not touch dependencies. A liveness probe that checks
          # the database restarts every replica during a database blip.
          livenessProbe:
            httpGet: { path: /api/v1/health/live, port: 8000 }
            initialDelaySeconds: 15
            periodSeconds: 20
            failureThreshold: 3

          # Readiness checks real dependencies, so an unready replica leaves the
          # load balancer while staying alive to recover.
          readinessProbe:
            httpGet: { path: /api/v1/health/ready, port: 8000 }
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3

          # Investigations can take 30s+. Without a startup probe, a slow first
          # migration would trip the liveness probe and crash-loop.
          startupProbe:
            httpGet: { path: /api/v1/health/live, port: 8000 }
            periodSeconds: 5
            failureThreshold: 30

          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits:   { cpu: "2",  memory: 2Gi }

          securityContext:
            runAsNonRoot: true
            runAsUser: 1001
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }

          volumeMounts:
            - { name: tmp, mountPath: /tmp }

      volumes:
        - name: tmp
          emptyDir: {}

      # Investigations are long. Give in-flight work time to finish.
      terminationGracePeriodSeconds: 60
```

`readOnlyRootFilesystem: true` requires `LOG_TO_FILE=false` and a writable
`/tmp`.

### Service and ingress

Investigations routinely exceed default proxy timeouts, and SSE breaks under
response buffering:

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "300"
    nginx.ingress.kubernetes.io/proxy-buffering: "off"   # required for /chat/stream
```

The app already sends `X-Accel-Buffering: no` on streaming responses, but the
ingress annotation is needed for proxies that ignore it.

## The connection budget

This is the constraint most likely to bite at scale. Each replica holds **two**
pools:

```
total = replicas × (POSTGRES_POOL_SIZE + POSTGRES_MAX_OVERFLOW)   # ORM
      + replicas × POSTGRES_POOL_SIZE                             # checkpointer
```

At defaults with 8 replicas: `8 × 30 + 8 × 20 = 400` connections against a
typical `max_connections` of 100–500.

Do **not** raise `max_connections` as the first response — each connection costs
roughly 10 MB of backend memory, converting a connection problem into an
out-of-memory problem on the database host. Instead:

1. Lower `POSTGRES_POOL_SIZE` per replica and add replicas.
2. Put PgBouncer in transaction mode in front of the cluster.

If you use PgBouncer, note that transaction-mode pooling breaks prepared
statements. Aegis already sets `prepare_threshold=None` on the psycopg
checkpoint pool for this reason; verify your asyncpg configuration does the
equivalent.

## Scaling

**Aegis is stateless.** All state is in PostgreSQL, including conversation
history via LangGraph checkpoints. Scale horizontally without sticky sessions.

| Bottleneck | Symptom | Response |
|---|---|---|
| LLM provider | `aegis_llm_requests_total{outcome="error"}` rising | Raise provider quota; add fallback models |
| Database connections | Pool saturation alert | Lower per-replica pool; add PgBouncer |
| Vector search | `aegis_retrieval_duration_seconds{stage="vector"}` p95 rising | Tune HNSW `ef_search`; add read replicas |
| CPU | Sustained throttling | More replicas |

Workers: **one uvicorn worker per container**, scaled by replica count. Multiple
workers per container multiply the connection count while sharing one memory
limit, and make Prometheus multiprocess mode necessary. If you do run several,
set `PROMETHEUS_MULTIPROC_DIR` — otherwise each worker reports only its own
slice.

### Read replicas

Retrieval is read-only and the largest query load. Point `POSTGRES_HOST` at a
replica for search-heavy deployments, but keep writes (ingestion, incidents,
checkpoints) on the primary — the current code uses a single DSN, so splitting
requires adding a second engine.

## Zero-downtime deploys

1. Make migrations backward compatible: add columns nullable, do not drop
   anything the previous version reads. Old and new replicas run concurrently
   during a rollout.
2. Roll out with `maxSurge: 1, maxUnavailable: 0`.
3. Watch readiness — an unready replica takes no traffic.
4. `terminationGracePeriodSeconds: 60` lets in-flight investigations finish.

A migration that drops a column the previous version still reads will error on
every request served by an old replica during the rollout window.

## Backups

```bash
pg_dump -Fc -d aegis > aegis-$(date +%F).dump
```

Embeddings are the expensive part to lose — regenerating them means paying for
every chunk again. They are also fully reproducible from source documents if you
keep those in version control, which is the cheaper insurance.

Checkpoint tables (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`) hold
conversation history. Losing them loses transcripts, not incidents or documents.

## Post-deployment checklist

```bash
make check                                  # config and dependency reachability
curl -sf localhost:8000/api/v1/health/ready | jq
curl -sf localhost:8000/metrics | grep aegis_app_info
aegis stats                                 # confirm the corpus is indexed
```

Then verify end to end:

```bash
aegis search "a symptom you know is documented"
```

If that returns nothing, the index is empty or the service filter is wrong —
fix it before anyone relies on the agent, because an ungrounded agent still
answers.
